02   Pipeline Architecture

Three PM2 processes work together. The main backend cron fires every hour and pushes three BullMQ jobs into Redis. The worker dequeues them and calls both data sources independently — a failure in one does not abort the other.

easyhyr-backend (PM2 #0, port 3000) └─ node-cron › fires at 0 * * * * (every hour, minute :00, UTC) └─ addJobToQueue( query, "United States" ) × 3 queries per cycle └─ BullMQ › queue: job-fetch-queue (Redis 127.0.0.1:6379) jsearch-worker (PM2 #1) └─ BullMQ Worker › dequeues each job │ ├─ Source A — JSearch API (RapidAPI, HTTPS external) │ └─ on 429 / error › log warning, continue (does not abort) │ └─ Source B — JobSpy Scraper (PM2 #2, localhost:8001) └─ jobspy › Indeed · LinkedIn · Google · Glassdoor · ZipRecruiter │ ├─ JobNormalizer › unify field names from both sources └─ JobStorage › upsert into PostgreSQL (dedup by apply_link)

05   Cron Schedule & Queries

The cron job in src/cron/job.cron.ts enqueues three BullMQ jobs per cycle. Each job runs through the full pipeline (JSearch + scraper) independently.

Query TermLocationCron ExpressionUTC Fire TimesEst. Jobs / Cycle
"jobs"United States0 * * * *00:00, 01:00 … 23:00~100–500
"developer"United States0 * * * *00:00, 01:00 … 23:00~100–500
"engineer"United States0 * * * *00:00, 01:00 … 23:00~100–500

Total potential ingestion per day (scraper only, while JSearch is down): ~600–4,500 new jobs depending on jobspy yield per cycle. Duplicates are silently skipped via upsert on apply_link.

To add queries or change the target location, edit lines 5–6 of src/cron/job.cron.ts:

const QUERIES = ["jobs", "developer", "engineer"];  // add search terms here
const DEFAULT_LOCATION = "United States";           // change target region here

To add a secondary location (e.g., India), duplicate the query loop with a different location constant.

10   Operational Runbook

SSH into server

ssh ubuntu@43.205.129.136 -i ~/Downloads/easyhyrbackend.pem

Check all process status

pm2 list

View live logs

# Worker — job processing output
pm2 logs jsearch-worker --lines 100

# Scraper — Python FastAPI access log
pm2 logs jobspy-scraper --lines 50

# Backend — cron + API request log
pm2 logs easyhyr-backend --lines 50

Deploy a code change

cd /home/ubuntu/easyhyr-backend
git pull origin master
npm run build
pm2 restart jsearch-worker        # picks up new dist/workers/
pm2 restart easyhyr-backend       # picks up new dist/cron/, dist/app.js
pm2 restart jobspy-scraper        # only needed if scraper-service/main.py changed

Manually trigger a job fetch (skip the cron)

# Push a job directly onto the BullMQ queue via Redis
redis-cli lpush 'bull:job-fetch-queue:wait' \
  '{"name":"fetch-jobs","data":{"query":"react developer","location":"United States"},"opts":{"attempts":3},"timestamp":0,"delay":0,"priority":0}'

# Worker will dequeue and process it within seconds

Test the Python scraper directly

curl "http://localhost:8001/scrape?query=software+engineer&location=United+States" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(len(d),'jobs returned')"

Check queue depth

redis-cli llen 'bull:job-fetch-queue:wait'      # jobs waiting to be processed
redis-cli zcard 'bull:job-fetch-queue:failed'   # jobs that errored

Clear the failed jobs queue

redis-cli zremrangebyscore 'bull:job-fetch-queue:failed' '-inf' '+inf'

Check live DB job count

cd /home/ubuntu/easyhyr-backend
node -r module-alias/register -e "
const { prisma } = require('./dist/lib/prisma');
async function run() {
  const total = await prisma.job.count();
  const latest = await prisma.job.findFirst({ orderBy: { created_at: 'desc' }, select: { created_at: true } });
  console.log(total, 'jobs — latest:', latest?.created_at);
  process.exit(0);
}
run();
"

Restart Redis (if connection refused)

sudo systemctl restart redis-server
redis-cli ping   # should return PONG

11   Known Issues

⚠
JSearch API — HTTP 429 Rate Limit (Active) The RapidAPI subscription for JSearch has exhausted its monthly request quota. All JSearch calls return 429. The pipeline has been patched to fall through to the scraper on failure, so ingestion continues via JobSpy. To restore JSearch: check usage at rapidapi.com under the JSearch subscription and upgrade the plan or wait for the monthly reset. Once restored, expect ~200 additional jobs per query cycle.
⚠
Google Jobs, Glassdoor & ZipRecruiter — Near-Zero Yield All five sites are configured in jobspy but current scrapes only return results from Indeed and LinkedIn. This may be due to bot-detection changes on those platforms or regional restrictions. Investigate by running a direct scrape with site_name=["glassdoor"] in isolation.
ℹ
employment_type — 30+ Raw Variants, Not Normalised Both sources return different string formats for what is effectively 5 categories. The frontend maps these at query time, but the DB stores raw values. A one-time migration + normalisation on write would make filtering more reliable.
ℹ
Skills Table Empty — No Skill-Based Filtering The easyhyr_job_skill_tags table has no records. The skills filter on the frontend always returns 0 results. Jobs from neither source include structured skill tags; extraction would require NLP post-processing on the description field.
ℹ
posted_within Filter Inaccurate The filter compares against created_at (DB insert time) rather than the job's original posting date. All jobs appear old relative to any date filter. Fix requires storing the original post date from the source and filtering against that.
ℹ
60% of Jobs Have No Country Code 4,934 records have a null country field. These are primarily JSearch jobs where the geocoding was not returned. Location-based filtering on the frontend uses a broader location text search as a workaround.
