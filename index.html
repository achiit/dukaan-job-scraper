Architecture Overview

The pipeline consists of three independent processes managed by PM2. The main backend cron schedules work into a BullMQ queue backed by Redis. The worker dequeues jobs and calls both data sources in parallel.

easyhyr-backend (PM2 id:0, port 3000) └─ node-cron » fires at 0 * * * * (every hour, minute zero) └─ addJobToQueue( query, "United States" ) ×3 queries └─ BullMQ » job-fetch-queue (Redis 127.0.0.1:6379) jsearch-worker (PM2 id:1) └─ BullMQ Worker » dequeues jobs ├─ [A] JSearch API (RapidAPI, HTTPS) │ └─ on 429 / failure » log warning, continue ↓ └─ [B] jobspy-scraper (PM2 id:2, localhost:8001) └─ jobspy » scrape Indeed · Google · LinkedIn · Glassdoor · ZipRecruiter └─ normalize » saveJobsToDB (PostgreSQL)

Scheduling & Queries

The cron job in src/cron/job.cron.ts runs three queries per cycle. Each query is pushed as a separate BullMQ job, processed independently by the worker.

QueryLocationFrequencyJobs per run (est.)
"jobs"United StatesEvery hour at :00~100–500
"developer"United StatesEvery hour at :00~100–500
"engineer"United StatesEvery hour at :00~100–500

Cron expression: 0 * * * * — fires at minute 0 of every hour (00:00, 01:00, 02:00 … UTC).

To add more queries or change the location, edit src/cron/job.cron.ts:

const QUERIES = ["jobs", "developer", "engineer"];  // add terms here
const DEFAULT_LOCATION = "United States";           // change target region here

Operational Runbook

Check all process status

ssh ubuntu@43.205.129.136 -i ~/Downloads/easyhyrbackend.pem
pm2 list

View live logs

# Worker (job processing)
pm2 logs jsearch-worker --lines 100

# Scraper (Python FastAPI)
pm2 logs jobspy-scraper --lines 50

# Backend (cron output)
pm2 logs easyhyr-backend --lines 50

Restart after a code deploy

cd /home/ubuntu/easyhyr-backend
git pull origin master
npm run build
pm2 restart jsearch-worker
pm2 restart easyhyr-backend
pm2 restart jobspy-scraper    # only if main.py changed

Manually trigger a job fetch (bypass cron)

# Queue one fetch directly via Redis
redis-cli lpush 'bull:job-fetch-queue:wait' \
  '{"name":"fetch-jobs","data":{"query":"react developer","location":"United States"},"opts":{"attempts":3},"timestamp":0,"delay":0,"priority":0}'

# The worker will pick it up automatically within seconds

Test the scraper directly

curl "http://localhost:8001/scrape?query=software+engineer&location=United+States" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(len(d),'jobs')"

Check queue depth

redis-cli llen 'bull:job-fetch-queue:wait'      # waiting
redis-cli zcard 'bull:job-fetch-queue:failed'   # failed

Clear failed jobs from queue

redis-cli zremrangebyscore 'bull:job-fetch-queue:failed' '-inf' '+inf'

Check database job count

cd /home/ubuntu/easyhyr-backend
node -r module-alias/register -e "
const { prisma } = require('./dist/lib/prisma');
prisma.job.count().then(n => { console.log(n, 'jobs'); process.exit(0); });
"

Known Issues

⚠
JSearch API — 429 Rate Limit (Active)
The RapidAPI subscription for JSearch has hit its monthly request quota. All JSearch calls return HTTP 429. The pipeline continues to ingest jobs via the JobSpy scraper (Source B). To restore JSearch: log in to RapidAPI, check usage under the JSearch subscription, and upgrade or wait for the monthly reset.
ℹ
Skills table empty
The easyhyr_job_skill_tags table has no data. Skill-based job filtering always returns 0 results. Jobs fetched by the scraper do not include structured skill tags — these would need to be extracted via NLP post-processing.
ℹ
Posted-within filter inaccurate
The posted_within filter compares against created_at (when the job was stored) rather than the job's original post date. All jobs appear old relative to the filter threshold.
